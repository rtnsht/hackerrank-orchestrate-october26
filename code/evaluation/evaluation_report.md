# Evaluation Report — Mastra Deletion-Audit Agent

All numbers below are produced by `npm run evaluate`, which runs the **real Mastra workflow** (`src/main.ts`) on the
32 public samples and on the participant-created cases, then scores the predictions with `evaluation/score.ts`.

## How the metrics are computed

### Scoring rules

- **Case-level status accuracy** — `deletion_status` equals the reference.
- **Step precision / recall / F1** — a predicted step matches a reference step only if `phase`, `system_id`,
  `resource_id`, `operation`, `state` and `evidence_id` are all equal (order-independent). A second F1 ignores
  `evidence_id` to separate *what* was found from *which file proves it*.
- **Field-level accuracy** — positional comparison of each field of step *i* in prediction vs reference (a missing or
  extra step shifts later positions, so this is the strictest view).
- **Sequence accuracy** — the case has the same number of steps and every shared step appears in the same relative
  order (status must also match).
- **Exact case match** — status and the full ordered `steps_json` array are identical.

### Data used

- Public samples: `dataset/sample_deletion_requests.csv` vs `dataset/sample_output.csv` (organizer-provided answers
  for the 32 public samples; used only for scoring, never as predictions or hard-coded labels).
- Participant-created cases: a synthetic dataset generated by `evaluation/custom-cases.ts` (fictional `example.com`
  identities) with hand-derived expected answers.

## Additional evaluation cases created by the team

### Why these cases

The public samples mix many behaviours in each case. The custom cases isolate one behaviour each so that a regression
points at a single rule: historical identifiers, replication drift, point-in-time cut-off, tombstone redaction,
remediation ordering with flows and restores, look-alike decoys, and multilingual non-deletion requests.

### Cases

The table in the metrics block lists all eight cases with what each checks and the predicted vs expected outcome. The
fixture data (evidence files in the same formats as `dataset/evidence/`: resource-export JSON, failover-replica SQL,
snapshot bundle JSON, readback log) is written by `writeCustomDataset()` into `code/.runs/custom_dataset/` and audited
with `DATASET_DIR` pointing at it.

## Independent verification of the hard cases

The 518 evaluation cases have no public answers, so the hardest 17 were checked by an **independent two-stage review**
run as a multi-agent workflow (10 agents):

1. **Investigators** (blind to the engine and its code) derived the expected status and steps for each case directly
   from the raw dataset — opening screenshots and PDFs, grepping every identifier variant, checking capture times.
2. **Adjudicators** compared each investigator answer with the engine output and settled every discrepancy from the
   raw evidence, stating a general rule (no case ids) for the engine.

### Cases reviewed

- The 12 hand-crafted evaluation cases built around screenshots / PDFs: `case_33`, `34`, `35`, `39`, `45`, `46`,
  `50`, `52`, `53`, `55`, `61`, `63`.
- Five January cases where the first engine version produced no account step: `case_282`, `526`, `527`, `529`, `531`.

### Rules adopted from the review

| Adjudicated rule | Engine change |
| --- | --- |
| Every in-scope account must be verified even when no evidence available at `audit_at` proves its state | in-scope records without citeable state get their required final-state verification in INCOMPLETE plans (fixed all five January cases) |
| A finding must cite an item captured by `audit_at`; prefer the pre-audit file when both show the record | state is taken only from files captured by `audit_at` (e.g. `case_527` now cites `evidence_62`, not a later bundle) |
| Scope each case to its own request: never carry a record introduced by a later request back into an earlier case | linking evidence must be dated at or before `audit_at`; later readbacks may attribute records only when the person has no later deletion request (fixes `case_46`, `case_52`; `case_33` no longer re-lists the June export) |
| A COMPLETE case never contains a verification without evidence | unverified records are excluded from COMPLETE plans (`case_46`) |
| A link available at `audit_at` outranks a post-audit attribution | link reasons are ordered accordingly |

### Rules rejected

| Suggestion | Why it was rejected |
| --- | --- |
| Infer `account_0NN` for hand-crafted users from the naming pattern of the public samples | not grounded in participant evidence (the adjudicator for `case_63` agreed); would be a case-family shortcut |
| Resolve an account from `sample_output.csv` for the same person | organizer answers must never feed predictions |

### Remaining disagreement

One point stayed split between reviewers: whether records that only a September readback ties to a person (whose
case was audited months earlier, with no later request) belong to that case. The engine includes them as
verification-only steps — never findings, never cited — which matches four of the five investigator answers.

## Known limitations

### Not recoverable from participant data

- Three sample reference steps name records that appear in **no** participant-visible file or activity
  (`account_004`, `audit_record_6645`, `audit_record_5569`); no evidence-based method can produce them.
- When several requests of the same status are reported in the same worker batch and their primary profiles carry no
  identifier anywhere, the attribution is a deterministic tie-break (one sample case, `case_23`, picks the other
  request's profile).

### Design trade-offs

- OCR + screen-aware rules interpret the 11 screenshots deterministically; with a vision model key the Mastra vision
  agent replaces that step. Row-level OCR association is deliberately not used for identity (catalog links and
  single-subject screens are), trading recall for precision on dense list screens.
- A request whose email resolves to no known person yields `COMPLETE` with no steps (nothing can be attributed).
